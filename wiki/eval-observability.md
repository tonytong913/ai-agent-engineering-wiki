# Eval 与 Observability

## 交流定位

Eval 和可观测性决定 Agent 是否能持续迭代。技术交流方会关注你如何定义质量、发现回归、定位失败，并把模型、prompt、工具、检索和环境问题区分开。

## 核心概念

- **Offline eval**：用固定任务集评估模型、prompt、工具和系统改动。
- **Online eval**：在真实流量中监控质量、延迟、成本和失败率。
- **Trace**：记录一次任务中的消息、工具、检索、评分和错误。
- **LLM-as-judge**：用模型评分，但需要校准和偏差控制。
- **Regression**：系统改动后质量下降，需要可重复检测。

## 工程实现

- 为每次 Agent run 生成 run id，并记录 span：模型调用、工具调用、检索、评分。
- 指标至少包含成功率、错误率、延迟、token、成本、工具失败率、用户反馈。
- golden set 要覆盖高频任务、边界任务和历史事故样本。
- LLM-as-judge 应结合 rubric、少量人工标注和一致性检查。
- 失败归因要区分模型误判、检索缺证、工具异常、权限拒绝和环境波动。

## 常见技术交流问题

- 如何构建 Agent 回归测试集？
- LLM-as-judge 有哪些风险？
- 线上 Agent 需要监控什么？
- 如何从 trace 定位失败原因？

## 追问点

- 如何发现 prompt 修改导致的隐性回归？
- 如何评估工具调用质量？
- 成本突然上涨时如何定位？

## 项目表达

可以讲一个“Agent 质量看板”的项目：把 trace、成本、延迟、工具失败、judge 分数和用户反馈聚合，支撑上线门禁和回归排查。
